# Contributing

Thank you for helping improve NARA documentation.

## Before opening a change

1. Read [Current state](docs/CURRENT_STATE.md) and
   [Legal notice](LEGAL.md).
2. Follow the mandatory
   [repository maintenance protocol](docs/MAINTENANCE.md).
3. Use active v4 code and verified Base state as sources of truth.
4. Do not copy from retired v3 contracts or historical documentation.
5. Keep language understandable to a first-time crypto user.
6. Run the checks required for the change class.

## Documentation requirements

- Label each feature as live, unavailable, planned, deferred, or retired.
- Give exact addresses only when verified.
- Explain unfamiliar terms or link the glossary.
- Put risks beside related functionality.
- Do not promise dates, prices, returns, rewards, safety, or regulatory status.
- Do not provide personalized financial guidance.
- Never include keys, seed phrases, credentials, private RPC URLs, or personal data.

## Pull requests

Use a focused branch and pull request. Describe the code or onchain evidence
supporting factual changes. Required checks must pass. Security reports belong
in private email, not pull requests or issues.

The pull request must identify its primary change class and confirm every
affected file in the maintenance protocol's synchronization matrix was reviewed.

By contributing, you agree that your contribution is licensed under the
repository's MIT License.
